# ByteOJ 新生方向探索开发提示词

> 本文不是产品宣传文案，而是一组未来可以直接交给 AI 编程助手使用的开发提示词。建议按顺序执行，每次只完成一个阶段，不要一次要求生成完整系统。

## 使用方式

每次开发前，把“全局约束”和对应阶段提示词一起发给 AI。开发完成后先运行、检查和试用，再进入下一阶段。

不要让 AI 一次性创建所有方向、所有页面和所有交互。第一版只实现前端、算法、数据分析、软件测试四个方向中的最小体验。

## 全局项目背景

你正在一个已有的 Vue 3 + TypeScript + Vue Router 项目中开发 ByteOJ 功能。项目是个人试点，不依赖学院、教师、社团或管理员批量导入用户。目标用户是刚进入大学、对计算机方向不了解的新生。

ByteOJ 不要被实现成 LeetCode 替代品、综合校园管理系统、通用 AI 聊天网站或职业性格测试平台。当前目标是：

> 让一个不知道从哪里开始的新生，用较短时间低成本体验几个计算机方向，并得到下一步可以执行的建议。

## 全局产品原则

1. 先让用户做事，再解释方向，不要先展示大段介绍。
2. 每个体验控制在 3 到 10 分钟，完整探索控制在 30 到 40 分钟。
3. 第一次体验不要求注册，不要求登录，不要求安装软件。
4. 不把一次体验结果写成“你适合某职业”，只说“你可能更愿意继续尝试某方向”。
5. 困难不等于没有兴趣，完成得快也不代表一定适合。
6. 每个体验必须有明确完成条件、即时反馈和下一步动作。
7. 不使用复杂 AI 作为第一版依赖。第一版使用固定内容、规则和本地状态即可。
8. 不破坏现有路由、导航、题库、考试和判题功能。
9. 优先复用现有 Vue、TypeScript、Tailwind/DaisyUI、路由和消息提示模式。
10. 所有新增内容要考虑移动端，避免固定宽度和横向溢出。

## 全局交互模型

每个体验任务统一包含：

- `id`：任务唯一标识；
- `direction`：所属方向；
- `title`：任务标题；
- `estimatedMinutes`：预计时间；
- `intro`：任务开始前的一句话；
- `steps`：任务步骤；
- `interactionType`：交互类型；
- `completionRule`：完成条件；
- `successFeedback`：完成反馈；
- `difficulty`：入门难度；
- `nextActions`：完成后的下一步。

第一版允许的交互类型只有：

- 选择题；
- 拖拽或排序；
- 参数调整；
- 代码填空；
- 运行结果判断；
- 简单数据可视化选择。

## 阶段一：代码和现有项目勘察

### 提示词

```text
请先阅读当前项目，不要立即修改代码。

项目背景：这是一个已有的 Vue 3 + TypeScript + Vue Router 项目 ByteOJ。现在要增加“新生方向探索”功能，但必须保持现有算法题库、判题、考试、课程和导航正常工作。

请检查并报告：
1. 当前 package.json 使用的框架和 UI 方案；
2. router/index.ts 的路由结构；
3. NavbarView.vue 的导航结构；
4. 是否已有可复用的消息提示、卡片、弹窗和 Markdown 组件；
5. 当前是否已经存在 localStorage 状态模式；
6. 哪些现有页面适合作为方向探索的容器；
7. 新增文件应该放在哪个目录。

只输出勘察结果、拟修改文件和风险，不要改代码。
```

## 阶段二：先创建方向地图

### 目标

创建一个轻量入口，让用户先看到可以体验的方向，但不要把页面做成专业术语列表。

### 提示词

```text
请在当前 ByteOJ 项目中实现“新生方向探索”第一阶段：方向地图。

产品目标：让不了解计算机方向的新生选择一个低门槛体验，而不是阅读长篇职业介绍。

要求：
1. 新增一个独立 Vue 页面，例如 DirectionExploreView.vue；
2. 增加一个独立路由，例如 /explore；
3. 在现有导航的合适位置增加入口，但不要把它命名成“职业测试”；
4. 页面标题使用“先试试看，你可能对什么感兴趣？”之类的自然表达；
5. 第一版只展示四个可体验方向：前端、算法、数据分析、软件测试；
6. 页面同时展示后端、数据库、网络安全、嵌入式等“即将开放”方向，但这些方向不能伪装成已经完成；
7. 每个方向卡片只显示：一句话说明、预计时间、体验入口；
8. 不要求登录，不调用 AI，不接后端接口；
9. 使用现有项目的样式习惯，移动端可用；
10. 点击体验后进入对应任务页或任务状态；
11. 增加空状态、加载状态不需要伪造网络请求；
12. 不修改现有题库和考试页面。

完成后请报告：新增文件、路由变更、导航变更、如何手动验证。
```

## 阶段三：建立通用体验任务组件

### 目标

不要为每个方向复制一套页面。先做可配置的任务容器。

### 提示词

```text
请在现有 ByteOJ 项目中实现一个可复用的“方向体验任务容器”。

要求：
1. 将任务定义放在独立的 TypeScript 数据文件中，不要把所有任务内容硬编码在模板里；
2. 创建清晰的类型，例如 Direction、ExperienceTask、ExperienceStep；
3. 组件支持任务标题、预计时间、当前步骤、进度、操作区、反馈区、完成状态；
4. 支持选择题、排序题、参数调整、代码填空、运行结果判断这几类基础交互；
5. 每个任务必须有明确的完成规则；
6. 用户答错时给提示，不要直接结束任务；
7. 完成任务后显示“你刚才体验了什么”和“下一步可以做什么”；
8. 记录开始时间、完成时间、是否重试、是否完成；
9. 使用 localStorage 保存匿名体验记录，页面刷新不能丢失当前任务；
10. 不要引入新的大型依赖；
11. 不要实现职业诊断、人格测试或 AI 推荐。

先实现组件和类型，使用一个最简单的示例任务验证，不要一次写四个方向。
```

## 阶段四：实现前端体验

### 产品设计

任务例子：修改页面文字、颜色和按钮行为，立即看到视觉反馈。

### 提示词

```text
请基于现有的通用方向体验任务容器，实现“前端入门体验”。

用户不需要知道 HTML、CSS、JavaScript 术语。任务流程如下：
1. 给用户一个简单的个人介绍卡片；
2. 让用户选择卡片颜色；
3. 让用户修改标题文字；
4. 让用户选择按钮点击后的文字；
5. 点击预览按钮，实时显示最终效果；
6. 三项完成后判定任务完成。

完成反馈必须说明：
- 用户刚才修改的是页面和交互；
- 这类工作通常属于前端开发；
- 前端的特点是结果反馈快、能直接看到页面变化。

完成后给出三个自评选项：
- 我喜欢立刻看到效果；
- 还可以，想再试一个；
- 我更想了解数据和逻辑。

自评只用于记录，不要直接宣布用户适合前端。
```

## 阶段五：实现算法体验

### 产品设计

算法体验必须从简单逻辑开始，不能一上来就是完整竞赛题。

### 提示词

```text
请基于通用体验任务容器，实现“算法入门体验”，并复用现有项目的代码编辑器或判题能力，但不要影响正式题库。

任务流程：
1. 用生活化问题展示“如何从一组数字中找到最大值”；
2. 让用户拖拽或选择正确的处理步骤；
3. 让用户补充极少量伪代码或代码空格；
4. 如果当前项目已有安全的运行/判题接口，可以运行固定测试数据；
5. 如果接入判题风险较高，第一版使用本地规则校验，不要为了体验引入新的后端系统。

完成反馈必须说明：
- 用户刚才体验的是把问题拆成步骤；
- 算法学习需要逻辑、代码基础和持续练习；
- 第一次觉得困难不代表不适合。

自评选项：
- 我喜欢一步步解决问题；
- 逻辑能理解，但代码有点难；
- 我觉得这个过程比较枯燥；
- 我想先试试别的方向。
```

## 阶段六：实现数据分析体验

### 产品设计

先不用 Python 执行环境，使用内置的小型数据集和图表/选项判断。

### 提示词

```text
请基于通用体验任务容器，实现“数据分析入门体验”。

不要接入真实 Python 执行环境，也不要要求用户安装任何工具。

任务流程：
1. 展示一组简单的月度数据，例如学习时长和考试成绩；
2. 让用户选择最能表达趋势的图表；
3. 让用户判断哪个月份出现异常；
4. 让用户从三个结论中选择最可靠的一项；
5. 展示一个简单的结果图表。

完成反馈必须说明：
- 数据分析不是单纯看图，而是从数据中找规律并验证结论；
- 真实学习还会涉及表格、SQL、Python 和统计基础；
- 当前体验只是认知示例，不代表已经掌握数据分析。
```

## 阶段七：实现软件测试体验

### 产品设计

用一个简单的登录表单或购物车页面，让用户发现需求和实现不一致的地方。

### 提示词

```text
请基于通用体验任务容器，实现“软件测试入门体验”。

任务流程：
1. 展示一个简单登录表单和需求说明；
2. 提供若干输入场景：正确账号、错误密码、空输入、超长输入、特殊字符；
3. 让用户选择哪些场景应该测试；
4. 展示一个隐藏的缺陷，让用户通过测试发现它；
5. 让用户选择这个问题属于输入校验、提示信息还是权限逻辑。

完成反馈必须说明：
- 软件测试不只是“找 Bug”；
- 测试需要根据需求设计场景并验证系统行为；
- 细心、愿意重复验证可能是一个有价值的倾向，但不能据此做职业诊断。
```

## 阶段八：探索结果页

### 提示词

```text
请实现“新生方向探索结果页”，读取当前浏览器 localStorage 中的体验记录。

要求：
1. 展示用户体验过的方向；
2. 展示每个任务是否完成、用时、重试次数和用户自评；
3. 用“更愿意继续尝试”而不是“最适合职业”表达结果；
4. 如果用户只完成了一个方向，提示继续体验另一个方向；
5. 如果用户在某方向多次重试但仍愿意继续，标注为“有兴趣但需要基础”；
6. 给出明确的下一步按钮，例如再次体验、体验其他方向、进入基础练习；
7. 结果页不调用 AI，不生成长篇空泛报告；
8. 提供清除本地体验记录的按钮；
9. 移动端布局正常。
```

## 阶段九：新增方向时的模板

当需要增加后端、数据库、网络安全、嵌入式、移动端、游戏开发等方向时，先使用下面的提示词，不要直接要求实现复杂实验环境。

```text
请为 ByteOJ 新生方向探索增加“[方向名称]”的轻量认知体验。

重要限制：
1. 不实现生产级开发环境；
2. 不要求真实硬件、真实服务器或真实攻击目标；
3. 不引入大型运行时和新的基础设施；
4. 不声称用户已经掌握该方向；
5. 体验时间控制在 3 到 10 分钟；
6. 优先使用选择、排序、参数调整、静态案例和可视化反馈；
7. 完成后解释刚才体验对应的真实工作内容；
8. 给出继续学习需要的工具、基础和下一步资源；
9. 接入已有通用任务容器和 localStorage 记录；
10. 先输出设计和风险，不要直接修改代码。

请先回答：
- 这个方向最适合被简化成什么认知任务；
- 哪些内容无法在浏览器中真实表达；
- 任务是否可能误导新生；
- 是否值得现在开发；
- 如果值得，最小交互是什么。
```

## 阶段十：质量检查提示词

```text
请检查刚完成的 ByteOJ 新生方向探索功能，不要先改代码。

重点检查：
1. 用户是否能在没有解释的情况下知道下一步；
2. 是否在第一次进入时暴露了过多专业术语；
3. 任务是否能在 3 到 10 分钟内完成；
4. 错误是否给出可理解的提示；
5. 完成后是否有立即反馈和下一步动作；
6. 是否把一次体验错误地包装成职业判断；
7. 刷新页面后记录是否还在；
8. 移动端是否横向溢出；
9. 是否破坏现有路由和导航；
10. 是否新增了不必要的依赖或后端接口。

请按“问题、影响、建议修改、严重程度”列出结果，发现问题后再等待我确认，不要直接进行大范围重构。
```

## 阶段十一：用户试用记录提示词

```text
请为 ByteOJ 新生方向探索准备一份手动试用记录表，不需要写代码。

记录以下信息：
1. 用户是否知道页面要做什么；
2. 从进入到开始任务用了多久；
3. 哪一步卡住；
4. 是否完成第一个任务；
5. 是否愿意尝试第二个方向；
6. 用户如何描述刚才体验的方向；
7. 用户觉得哪里有趣、哪里无聊、哪里困难；
8. 用户是否认为 ByteOJ 比直接搜索更方便。

最后给出判断：
- 继续优化当前方向；
- 换一个方向试验；
- 暂停开发方向探索，回到个人练习/考试工具。
```

## 最小开发顺序

不要同时开发全部方向，建议顺序如下：

1. 方向地图；
2. 通用体验任务容器；
3. 前端体验；
4. 算法体验；
5. 数据分析体验；
6. 软件测试体验；
7. 探索结果页；
8. 找真实新生试用；
9. 根据试用结果决定是否增加后端、数据库或网络安全。

如果前四个轻量体验不能让用户完成并愿意继续，不要继续增加方向数量。问题可能不是方向不够，而是“方向探索”本身没有形成足够强的用户需求。

## 明确禁止的一次性开发请求

不要向 AI 提出以下请求：

```text
请一次性帮我实现一个包含前端、后端、嵌入式、数据分析、网络安全、算法、移动端、游戏开发和 AI 的完整方向探索平台，并接入推荐系统、用户画像、排行榜和社区。
```

这个请求会导致页面和假功能快速增加，但无法验证新生是否真的愿意使用。
