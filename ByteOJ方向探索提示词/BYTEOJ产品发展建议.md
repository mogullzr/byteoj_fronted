# ByteOJ 产品发展建议

> 本文基于当前 `web/src` 前端代码、路由结构、页面交互和已接入的接口进行整理，结合 ByteOJ 目前主要在校内使用、用户规模较小的现实情况提出。重点不是继续增加功能，而是明确 ByteOJ 为什么值得用户持续回来。

## 一、审阅范围与当前产品事实

当前前端约有 127 个 Vue/TypeScript/JavaScript 文件，已经形成了一个功能较多的学习与竞赛系统。主要模块如下：

| 模块 | 当前已有能力 | 产品成熟度判断 |
| --- | --- | --- |
| 算法题库 | 算法题分页、关键词/难度/标签/来源筛选、题目详情 | 有核心能力，但用户路径仍偏“题库浏览” |
| 在线判题 | Ace 编辑器、多语言、调试/提交、异步判题、WebSocket 与轮询兜底 | 是 ByteOJ 最有技术含量的核心 |
| 算法学习辅助 | 提交记录、全站提交记录、题解、答疑、视频、错题入口、代码回放 | 功能齐全，但缺少统一学习流程 |
| 每日一题 | 抽卡式每日题、随机切换、难度展示 | 有习惯入口，但还没有和成长数据、复习任务连起来 |
| 竞赛 | 比赛列表、参赛、创建比赛、题目、排行榜、记录、Rating | 具备校内竞赛基础设施，是最可能形成校内壁垒的模块 |
| 考研题库 | 数学、408、政治题库，筛选、题目详情、错题本 | 内容入口完整，但需要更强的复习闭环 |
| 模拟考试 | 报名、考试须知、持久化绝对倒计时、答题、算法题、图片/摄像头、自动提交、成绩记录、答题卡 PDF | 功能量很大，但用户价值需要从“能考试”转为“能提升分数” |
| 课程 | 课程列表、课程内容、课程题目、记录、报名支付、支付轮询、学习群二维码 | 具备商业化雏形，但课程和题库/进度之间尚未形成统一系统 |
| 社区 | 发帖、Markdown、评论、回复、点赞、答疑、题解 | 有社区组件，但冷启动时容易显得空 |
| 实时聊天 | WebSocket 房间、在线人数、历史消息、重连 | 有基础设施，但单一公共房间的长期价值有限 |
| AI | 题目上下文聊天、模型切换、SSE 流式回答、个性化学习路径生成 | 技术接入存在，但目前更多是通用对话/文本生成 |
| 学习工具 | 代码回放、单链表动画、精确计时、搜索、应用中心 | 有特色，但多数不是主线留存功能 |
| 用户体系 | 登录、个人中心、博客、背景图、权限控制、比赛状态 | 基础完整，但成长档案尚未成为产品主界面 |

### 代码中体现出的几个重要事实

1. **算法判题是最完整、最接近核心产品的能力。** 编辑器已经处理多语言、异步任务、WebSocket、轮询、调试、提交和操作记录；这是 ByteOJ 不应该放弃的技术底座。
2. **题库、提交、题解、答疑、视频、错题分别存在，但没有组成“学习闭环”。** 用户可以完成一次提交，却不一定知道下一步学什么，也没有被系统自然地带回平台。
3. **每日一题是很好的留存入口，但目前主要是抽题和跳转。** 它没有和连续学习、知识点掌握、错题复习、校内排行榜形成强联系。
4. **竞赛中心拥有校内产品的关键雏形。** 当前有创建比赛、竞赛题目、排行榜、记录和 Rating，这比单纯复制一个公共 OJ 更适合在学校内建立关系网络。
5. **考研模块已经投入了大量开发成本。** 题库、模拟考试、错题本、成绩记录、答题卡和 PDF 都不是简单展示，因此不建议继续把它宣传成“还有一个题库”，而应该包装成可追踪的训练与复习系统。
6. **AI 学习路径目前是把选择结果发送给通用模型并流式展示文本。** 它可以作为辅助，但还没有读取用户提交记录、错题、课程进度或考试表现，因此目前不能称为真正的个性化系统。
7. **首页目前基本是帖子流。** 这会让新用户首先看到一个需要社区活跃度才能成立的模块，而不是看到算法训练、校内比赛或考研复习的价值。
8. **导航暴露了很多入口，但缺少主线分层。** 算法、考研、竞赛、课程、社区、AI、应用中心并列出现，功能多，却没有告诉用户“今天应该做什么”。

## 二、核心判断

ByteOJ 不应该把目标定成 LeetCode、牛客或 Codeforces 的替代品：

- 无法在全球题库规模上超过 LeetCode；
- 无法在招聘和公司资源上超过牛客；
- 无法在高强度国际竞赛生态上超过 Codeforces；
- 单纯增加 AI 聊天，也无法产生稳定差异化。

ByteOJ 更现实、更有机会的定位是：

> **面向普通高校学生的算法训练、校内竞赛、同伴协作和成长记录平台；同时提供可量化的考研训练闭环。**

这里真正要解决的不是“学生找不到题”，而是：

- 不知道从哪里开始；
- 不知道现在应该做什么；
- 做题遇到困难后没有合适的下一步；
- 坚持几天后失去反馈；
- 找不到同水平、同目标的同学；
- 老师或社团无法低成本组织训练和比赛。

## 三、最值得发展的产品方向

### 1. 算法方向：从“题库”变成“完成一条可见的训练路线”

ByteOJ 当前已经有题库筛选和判题能力，缺的不是更多题，而是学习编排。建议把算法主线设计为阶段式路线：

- C++ 与基础语法；
- 模拟、排序、前缀和、差分；
- 二分、双指针、滑动窗口；
- DFS、BFS、回溯；
- 贪心、动态规划；
- 图论、最短路、并查集；
- 竞赛专题与校赛训练。

每个阶段都应该包含：少量讲解、代表题、练习题、阶段测试、错题复习和完成状态。用户必须能看到“我在第几阶段，下一步是什么”，而不是只面对一个大题库。

### 2. 把每日一题升级为每日训练任务

保留每日一题的抽卡形式，但让它产生持续行为：

- 今日题目；
- 今日建议用时；
- 今日知识点；
- 提交后自动进入完成记录；
- 做错后进入复习队列；
- 连续完成天数；
- 本周完成率；
- 同班/同社团完成排名。

用户回来不是因为“平台有一题”，而是因为“今天的任务还没有完成”。

### 3. 把竞赛做成校内网络，而不是比赛列表

竞赛模块已经具备题目、排行榜、记录和 Rating 的基础，建议重点发展：

- 班级、学院、社团排行榜；
- 新生榜、周榜、月榜；
- 社团专属训练赛；
- 新生入门赛；
- 赛后自动生成题目通过率和常见错误报告；
- 比赛结束后自动进入个人复盘；
- 小组组队和训练房间；
- 教师/社团负责人一键布置比赛。

这类关系和数据是 LeetCode、牛客、Codeforces 很难替代的，也是 ByteOJ 在校内最有机会形成壁垒的地方。

### 4. 建立算法成长档案

用户中心不应该只展示个人资料、博客或历史信息，而应成为算法成长页面：

- 已完成题目数；
- 各知识点通过率；
- 最近提交趋势；
- 常见错误类型；
- 竞赛 Rating 曲线；
- 每日训练连续天数；
- 当前学习路线；
- 待复习题目；
- 与同目标用户的阶段对比。

这类数据不需要复杂 AI，依靠已有提交记录、题目标签、比赛记录和错题数据就能先做出第一版。

### 5. 考研模块：从“在线考试”升级为“分数提升系统”

考研模块已有数学、408、政治题库和模拟考试，不应只宣传“支持 AI 判卷”。更有吸引力的产品承诺应该是：

> 做完一套题后，知道自己能考多少分、错在哪里、下一周先补什么。

建议重点建设：

- 按章节和题型统计掌握度；
- 模拟考试时间分配分析；
- 客观题正确率趋势；
- 主观题步骤完整性记录；
- 错题自动归类；
- 薄弱章节复习清单；
- 历次模拟成绩曲线；
- 复习计划和完成率；
- 考试结束后的针对性再练习。

AI 判卷可以继续保留，但它应只是反馈工具，而不是核心卖点。考研用户更关心结果是否能帮助提分，而不是系统是否使用了 AI。

### 6. 课程模块要与练习和结果打通

课程当前已经有报名、支付、内容、题目和学习群等能力，但如果课程只是视频/资料页面，用户很难持续使用。建议课程必须关联：

- 课程章节对应的题目；
- 章节完成状态；
- 课后练习；
- 章节测验；
- 错题回顾；
- 学习时长和进度；
- 课程结业结果。

课程价值应该从“买了资料”变成“完成了一个可验证的学习项目”。

## 四、AI 应该做什么，不应该做什么

### 值得做的 AI

AI 只有在替用户减少真实工作时才值得保留：

1. 根据提交记录识别错误类型，例如越界、超时、边界遗漏、复杂度不合适。
2. 用户卡住时给分层提示：思路提示、关键性质、伪代码提示，而不是直接贴完整答案。
3. 根据已做题、错题和知识点掌握度推荐下一题。
4. 根据考试记录生成具体的复习优先级。
5. 对考研主观题做步骤完整性和得分点提示，并明确标注“仅供参考”。
6. 将一段错题记录整理成可复习的错因卡片。

### 暂时不值得优先投入的 AI

- 首页放一个大型 AI 入口；
- 让 AI 泛泛生成完整题解；
- 只根据用户手动选择的标签生成学习路径；
- 生成大量没有经过质量检查的题目；
- 把普通聊天机器人包装成“智能学习系统”；
- 为了展示模型名称而增加模型切换复杂度。

当前 `PersonalLearningView` 主要是把用户选择的标签发送给模型生成文本，`ChatBoxView` 主要是上下文聊天。下一步若要升级，关键不是换模型，而是把提交、错题、竞赛、课程和考试数据作为真实输入。

## 五、首页和导航应该怎么改

当前首页主要展示帖子流，这对冷启动社区不友好。建议登录后的首页改成学习工作台，直接展示：

- 今日算法任务；
- 当前学习阶段；
- 最近错题；
- 待复习题；
- 连续学习天数；
- 本周完成率；
- 即将开始的校内比赛；
- 当前班级/社团排名；
- 考研用户的下一项复习任务。

未登录用户首页可以展示：

- 当前校内训练活动；
- 公开比赛；
- 算法入门路线；
- 考研模拟入口；
- 平台能解决的具体问题。

导航建议压缩成几条主线：

- 算法学习；
- 竞赛；
- 考研；
- 课程；
- 社区；
- 我的成长。

AI、代码回放、数据结构动画、精确计时等放入“工具/辅助”，不要与主线并列竞争用户注意力。

## 六、建议的优先级

### P0：先解决“用户为什么回来”

1. 首页学习工作台。
2. 算法阶段路线和下一步任务。
3. 每日一题与连续学习记录。
4. 错题复习队列。
5. 竞赛后复盘页面。
6. 基于现有数据的个人成长档案。

### P1：建立校内传播和组织能力

1. 班级/学院/社团排行榜。
2. 教师或社团负责人布置训练。
3. 新生入门赛和周赛模板。
4. 训练完成率和成绩导出。
5. 组队训练房间。

### P2：提升考研闭环

1. 章节掌握度。
2. 模拟成绩曲线。
3. 错题复习计划。
4. 时间分配分析。
5. 主观题反馈和复习建议。

### P3：把 AI 接入真实数据

1. 提交错误分析。
2. 分层提示。
3. 个性化题目推荐。
4. 考研复习优先级。
5. 训练结果摘要。

## 七、暂时不要做的事情

- 不要继续无边界增加页面和入口；
- 不要试图复制所有 OJ 的题库和竞赛生态；
- 不要把通用 AI 聊天当成核心差异化；
- 不要在社区没有活跃度前投入大量社交功能；
- 不要优先做只有展示效果、不会产生复访的动画和装饰；
- 不要同时把算法、考研、课程、AI 宣传成同等重要的主线。

## 八、现实可行的校内落地方案

建议先选一个非常窄的目标群体：本校大一、大二计算机相关专业学生，尤其是准备参加蓝桥杯、校赛、考研或刚开始刷题的人。

可以设计一个 4 周活动：

1. 第 1 周：基础语法、模拟、排序。
2. 第 2 周：二分、前缀和、双指针。
3. 第 3 周：搜索、贪心、动态规划入门。
4. 第 4 周：校内线上赛和个人复盘。

每周由社团或老师发布训练任务，平台记录完成率和排行榜。活动结束后，学生能拿到一份成长报告，负责人能拿到一份数据报告。这样才有明确的传播对象、使用周期和结果。

## 九、最终产品判断

ByteOJ 不需要证明自己比所有平台都强。它需要在一个具体场景里比其他平台更方便：

> **在普通高校里，让一个原本不知道如何开始、也不容易坚持的学生，能够按路线完成算法训练，和同学一起参加比赛，并留下可见的成长记录。**

算法判题是底座，竞赛和校内关系是壁垒，学习路线和错题复习是留存，成长档案是反馈，考研模块是第二条业务线，AI 只负责在具体环节减少人工工作。

如果这条主线被做实，ByteOJ 就不必成为 LeetCode 的替代品，也有机会成为本校学生愿意持续使用的学习基础设施。
